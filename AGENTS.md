# AGENTS.md — 3D-планировщик металлической мебели

**Статус:** черновик плана, версия 0.1  
**Дата:** 2026-10-25  
**Назначение:** единый источник истины по продукту, архитектуре и порядку разработки.  
**Важно:** документ обновляется по мере принятия решений. Если решение меняется — сначала правим AGENTS.md, затем код.

---

## 1. Цель проекта

Самостоятельное веб-приложение — 3D-планировщик металлической мебели, не зависящее от CMS «Битрикс». Приложение разворачивается отдельно (Docker Compose) и в дальнейшем встраивается на сайт ссылкой, iframe или обратным прокси.

Пользователь:

1. Открывает страницу и сразу задаёт планировку помещения (прямоугольное или Г-образное, размеры в сантиметрах).
2. Видит каталог мебели по категориям и перетаскивает мебель на план.
3. Работает в разделённом экране: 2D-план и 3D-вид.
4. Двигает, поворачивает и точно позиционирует мебель.
5. Переходит на страницу оформления, где видит снимки 2D-плана и 3D-видов, вводит контакты и сохраняет PDF-счёт.
6. Может создавать много заказов, смотреть их список, скачивать PDF, отправлять заказ администратору и удалять.

Сотрудник через админку:

- видит все заказы и меняет их статусы;
- управляет иерархическим каталогом (разделы → товары);
- загружает 3D-модели и изображения;
- ведёт справочник свойств и параметров с защитой от дублей;
- настраивает реквизиты, PDF, уведомления и параметры планировщика.

## 2. Зафиксированные решения (ADR)

### ADR-001. Приложение независимо от «Битрикс»

**Решение:** никакого PHP, компонентов Битрикс и обращений к его API. Интеграция с сайтом — только на уровне размещения: ссылка, iframe или reverse proxy.  
**Следствие:** собственные пользователи, сессии, админка, файлы и БД.

### ADR-002. Backend — Node.js, весь код на JavaScript

**Решение:** Node.js 22 LTS, ESM, без TypeScript. React-компоненты — `.jsx`. Допускается JSDoc для сложных функций, но не обязательный.  
**Следствие:** общий пакет `packages/shared` с геометрией, схемами и расчётом цен используется и на клиенте, и на сервере.

### ADR-003. Хранилище — MySQL 8.4 в Docker

**Решение:** MySQL 8.4 LTS в отдельном контейнере, доступ только из внутренней сети Docker. ORM — Drizzle ORM + `mysql2`, миграции — `drizzle-kit`.  
**Следствие:** транзакции, внешние ключи, индексы, конкурентный доступ. JSON-файлы как БД не используем. JSON применяем только как тип поля для снимков (room, order snapshot) и настроек.

### ADR-004. Docker Compose — единственный способ запуска

**Решение:** локальная разработка, тесты и продакшен запускаются через Docker Compose. Обязательные сервисы: `db`, `migrate`, `app`. Опционально: `adminer` (dev), reverse proxy (prod).  
**Следствие:** `docker compose up` из чистого состояния должен поднимать рабочее приложение; миграции применяются автоматически отдельным one-shot сервисом.

### ADR-005. Файлы (модели, изображения, PDF) — на диске, метаданные — в MySQL

**Решение:** бинарные файлы лежат в volume `uploads/`, в БД хранятся записи таблицы `files` (путь, MIME, размер, SHA-256, владелец, публичность).  
**Следствие:** бэкап = `mysqldump` + архив `uploads/`. Публичные модели/фото каталога отдаются статикой с кэшем, приватные изображения заказов и PDF — только через API с проверкой доступа.

### ADR-006. PDF генерируется на сервере

**Решение:** `pdfmake` (чистый JS, декларативный документ, таблицы, кириллица, изображения). PDF создаётся по неизменяемому снимку заказа и хранится в `uploads/orders/<order>/`.  
**Следствие:** PDF можно скачать позже, он не зависит от каталога и браузера пользователя. Клиент только готовит изображения.

### ADR-007. Редактирование — в 2D, 3D — для просмотра и презентации

**Решение:** точное перемещение, поворот и привязки выполняются на 2D-плане. В 3D доступны камера, выбор объекта, пресеты видов и, при необходимости, перемещение по полу (post-MVP).  
**Причина:** манипуляции в 3D мышью менее точны и заметно дороже в реализации.

### ADR-008. Гостевой режим покупателя в MVP

**Решение:** для оформления заказа регистрация не требуется. Заказ привязывается к подписанной гостевой сессии (cookie) и e-mail; список заказов и PDF доступны в этом браузере, а также админу/менеджеру. Ссылка с токеном для перехода между устройствами — post-MVP.  
**Следствие:** полноценные аккаунты покупателей (вход с другого устройства, история, восстановление) — этап после MVP. Админ/менеджер всегда имеют аккаунты.

### ADR-009. Один инстанс приложения

**Решение:** приложение рассчитано на один Node-процесс и одну БД. Горизонтальное масштабирование и S3 — post-MVP.  
**Следствие:** PDF-генерация, загрузки и фоновые задачи выполняются в процессе; тяжёлые операции — в `worker_threads`.

### ADR-010. 2D-план на SVG вместо Konva

**Решение:** 2D-редактор реализован на нативном SVG (React), без `react-konva`/canvas.
**Причина:** точные координаты в сантиметрах, доступность, отсутствие лишней зависимости; 100 OBB-объектов
отрисовываются без деградации. При росте сцены до тысяч объектов предусмотрен переход на canvas.
**Следствие:** drag/pan/zoom работают через pointer events и `viewBox`; размерные линии и подсветка коллизий —
обычные SVG-элементы.

### ADR-011. three.js напрямую вместо R3F

**Решение:** 3D-сцена собрана на `three` + `OrbitControls` в императивном компоненте.
**Причина:** нужен детерминированный захват кадров (`toDataURL`) и восстановление камеры для PDF;
без React-рендерера меньше зависимостей и проще кэш моделей.
**Следствие:** выбор объектов — raycasting; состояния сцены синхронизируются с Zustand через props.

### ADR-012. Оптимизация моделей в worker_threads

**Решение:** STL/GLB → сварка вершин → `meshoptimizer` simplify → GLB; оригинал не перезаписывается.
Облегчённый файл хранится отдельно, планировщик берёт `model.optimized.url`.
**Причина:** 176 тыс. треугольников тяжелы для мобильных устройств; упрощение до 50 тыс. сохраняет силуэт.
**Следствие:** статус/прогресс/ошибка видны в админке; при перезапуске незавершённые задачи помечаются
`failed` и могут быть повторены; откат — одной кнопкой.

## 3. Роли и права

| Роль | Доступ |
|---|---|
| Гость / покупатель | Планировщик, каталог, создание и сохранение своих заказов, список своих заказов в текущей сессии, PDF, отправка, удаление |
| `customer` (post-MVP) | То же + вход с другого устройства, постоянная история |
| `manager` | Только заказы: список, карточка, статусы, комментарии, PDF, экспорт. Без каталога и настроек |
| `admin` | Всё: заказы, каталог, свойства, модели, настройки, пользователи, аудит |
| Система | Миграции, seed, очистка черновиков, оптимизация моделей, бэкапы |

Правила:

- Все проверки прав — на сервере. UI-скрытие кнопок не считается защитой.
- Заказ доступен владельцу сессии, пользователю с тем же `user_id` или администратору.
- PDF и приватные изображения нельзя получить по прямому пути без токена/сессии.
- Удаление заказа пользователем — soft delete; purge выполняет админ или задача ретенции.

## 4. Пользовательские сценарии

### 4.1. Основной сценарий

1. Открытие `/` → диалог «Параметры помещения».
2. Выбор формы: прямоугольное / Г-образное.
3. Ввод размеров в см; подсказки и схема; проверка допустимости.
4. Создание проекта → редактор: слева каталог, по центру 2D/3D, справа инспектор.
5. Поиск/фильтрация, выбор товара, настройка опций (цвет, параметры), добавление на план.
6. Перемещение, поворот, привязка к сетке/стенам/другим предметам, точный ввод координат.
7. Исправление коллизий и предупреждений.
8. «Оформить заказ» → страница проверки: снимки 2D, 3D как видел пользователь, общий вид, фронт, профиль; таблица позиций и итог.
9. Ввод имени, телефона, e-mail, комментария, согласие на обработку ПД.
10. «Скачать PDF» → заказ сохраняется, PDF генерируется и скачивается.
11. «Отправить заказ» → статус `submitted`, уведомление админу, заказ появляется в админке.
12. «Мои заказы» → список; действия: PDF, отправить, удалить, копировать в новый.

### 4.2. Сценарий «несколько компоновок»

- Пользователь сохраняет заказ №1, возвращается в редактор, меняет расстановку, сохраняет заказ №2.
- Каждый заказ — независимый снимок: помещение, мебель, опции, цены, контакты, изображения, камеры.
- «Копировать» создаёт новый черновик из старого, не меняя оригинал.

### 4.3. Сценарий администратора

1. Вход `/admin/login`.
2. Дашборд: новые заказы, сумма, последние заказы.
3. Заказы: фильтры, карточка, смена статуса, комментарий, PDF, экспорт.
4. Каталог: дерево разделов, создание/перемещение/скрытие, товары.
5. Товар: наименование, SKU, цена, размеры, описание, изображения, 3D-модель, свойства, опции.
6. Калибровка модели: оси, масштаб, смещение, проверка габаритов.
7. Справочник свойств: типы, параметры, запрет дублей.
8. Настройки: реквизиты, PDF, VAT, нумерация, уведомления, лимиты.

## 5. Функциональные требования

### 5.1. Помещение

- Формы MVP: прямоугольник и L-образная комната.
- Прямоугольник: ширина `W`, глубина `D`, высота потолка `H` (по умолчанию 270 см).
- L-форма: общая ширина `W`, общая глубина `D`, ширина вертикальной части `w1`, глубина горизонтальной части `d1`. Полигон: `(0,0) → (W,0) → (W,d1) → (w1,d1) → (w1,D) → (0,D)`.
- Валидация: `W,D > 0`, `0 < w1 < W`, `0 < d1 < D`, минимальная ширина части 40 см, площадь > 1 м².
- Отображение площади и периметра; схема с подписями; кнопки «Отразить по X/Z».
- Толщина стен — визуальная (по умолчанию 10 см), внутренние размеры задаёт пользователь.
- Редактирование помещения после создания с предупреждением, если мебель перестаёт помещаться.
- Post-MVP: произвольный полигон, двери/окна/проёмы, колонны, несколько комнат.

### 5.2. Каталог

- Иерархия разделов произвольной глубины; сортировка; скрытие.
- Товар: наименование, SKU/артикул, цена, валюта, единица, ширина/глубина/высота в см, вес (опционально), краткое и полное описание, изображения, 3D-модель.
- Свойства из общего справочника; значения по типу; настройка «показывать в карточке/PDF/фильтрах».
- Опции, выбираемые покупателем (цвет, комплектация), с доплатой; обязательные/множественные.
- Поиск по названию/SKU; фильтры по разделу, цене, габаритам, свойствам; сортировка.
- Карточка товара: галерея, цена, размеры, описание, свойства, выбор опций, итоговая цена, «Добавить».
- Если у товара есть обязательные опции — модальное окно выбора до добавления.
- Один товар может быть добавлен много раз; количество (`qty`) редактируется в инспекторе и в заказе.

### 5.3. 2D-план

- Масштаб: 1 см модели = настраиваемое число пикселей; зум/пан, «вписать всё», сетка.
- Стены, пол, размерные линии, названия/габариты предметов.
- Перетаскивание из каталога и внутри плана.
- Выбор (клик, Shift+клик), мультивыбор рамкой, удаление, дублирование.
- Перемещение с привязкой к сетке (1/5/10 см), стенам, краям/центрам других предметов.
- Поворот: свободный, шаг 15°, кнопки ±15°/±90°, ввод угла.
- «Прижать к стене», выравнивание по краям/центрам, блокировка, копирование/вставка.
- Числовой инспектор: X, Z, угол, высота монтажа (если применимо), количество.
- Коллизии: пересечение с другими предметами и выход за полигон; подсветка, список предупреждений, запрет отправки заказа с критическими ошибками (настраивается).
- Undo/redo (минимум 100 шагов), горячие клавиши, автосохранение проекта в localStorage.
- Измерительная линейка (post-MVP).

### 5.4. 3D-вид

- Загрузка GLB/GLTF (бинарный) и STL; материалы: PBR-сталь по умолчанию, цвет из опции; материалы GLB сохраняются.
  Материал с `extras.tintable = false` не перекрашивается RAL-цветом (дерево, столешница, чёрные детали).
- Пол, стены, потолок (опционально), тени, окружение, нейтральный фон.
- Автоматическое скрытие/прозрачность стен, закрывающих обзор; переключатель.
- Орбитальная камера, пан, зум, пресеты: сверху, спереди, сбоку, изометрия, «вписать всё».
- Синхронизация выбора с 2D и инспектором.
- Сохранение состояния камеры пользователя для снимка заказа.
- Настройки качества (low/medium/high), ограничение DPR, пауза рендера в простое.
- Рендер «Рендер 3D» — настоящий (без тяжёлого рэйтрейсинга): суперсэмплинговая
  накопительная выборка (progressive render) — 6 проходов с микро-джиттером камеры
  (антиалиасинг) и источника света (мягкие полутени) усредняются в кадре;
  поверх кинопоставка — тон/насыщенность, свечение Orton, виньетка. На время
  рендера в сцену добавляются временные источники: усиленный глобальный свет,
  заполняющий, контровой (rim), локальный тёплый акцент с бликами на металле
  и мягкий «заполняющий» свет спереди-слева (приподнимает тени; его сила
  растёт вместе с «мягкостью теней»).
  Выход — полный размер окна, DPR до 2.25, без UI-слоёв; ~1–3 c на обычном ПК
  (за вычетом загрузки модели) с индикатором прогресса. Результат показывается
  прямо в окне 3D, скачивается в JPG и сохраняется в `sessionStorage`
  (`planner-render`) вместе с камерой и подписью проекта. На оформлении рендер
  попадает в PDF как снимок `view3d_user`; если проект изменился (подпись не
  совпадает) — делается обычный снимок.
- Мягкие проработанные тени: теневая камера главного света покрывает всю комнату
  (раньше из-за `far=500` предметы в дальней части не давали теней на полу);
  после накопления отдельно рендерится «теневая маска» — сцена только под
  направленным светом, белые материалы, белый фон и без плоскости-«горизонта»
  (иначе засвеченная даль затемняла бы весь кадр), маска слегка размывается
  минимальным узким размытием (только убрать ступеньки) и умножается на кадр
  (`composeShadow`, alpha ~0.5). Тени получаются мягкими и читаемыми, без
  «пелены» и без тёмных пятен; canvas-фактура поверх пола и стен больше не
  используется (выглядела неестественно). Постобработка приглушена: Orton 0.3,
  виньетка 0.12.
- Качество рендера настраивается в админке («Настройки → Рендер 3D»): пресет
  (Эконом/Стандарт/Качество/Максимум), число проходов, разрешение буфера,
  мягкость теней и сила постобработки. Значения хранятся в `settings.render`
  и применяются у всех посетителей через `GET /api/config`.
- Рядом с кнопкой «Рендер 3D» — шестерёнка с личными настройками рендера:
  пресеты и ползунки (проходы 2–16, буфер 40–100%, мягкость теней ×0.5–2,
  постобработка 0–2) + «Сбросить». Личные настройки (localStorage
  `planner-render-settings`) перекрывают админские и действуют только в этом
  браузере; закрытие — кликом снаружи или Escape.
- Post-MVP: перемещение/поворот прямо в 3D, walk-through, размерные линии в 3D.

### 5.5. Оформление заказа

- Отдельный маршрут `/checkout`.
- Сводка: помещение, площадь, список позиций (фото, название, опции, габариты, кол-во, цена, сумма), итог, НДС.
- Автоматическая генерация пяти изображений:
  1. `plan2d` — 2D-план без UI;
  2. `view3d_user` — 3D с камерой пользователя;
  3. `view3d_fit` — общий вид, все предметы в кадре;
  4. `front` — вид в фас (ортографический);
  5. `profile` — вид в профиль (ортографический).
- Прогресс загрузки изображений; возможность повторить при ошибке.
- Форма: имя, телефон, e-mail, компания/ИНН (опционально), комментарий, чекбокс согласия, ссылка на политику.
- Валидация телефона/e-mail на клиенте и сервере.
- «Скачать PDF» — создаёт/обновляет заказ и генерирует PDF.
- «Отправить заказ» — фиксирует заказ, статус `submitted`, уведомление.
- Нельзя отправить пустой заказ; критическая коллизия блокирует отправку с понятным сообщением.

### 5.6. Заказы покупателя

- `/orders` — список: номер, дата, статус, сумма, миниатюра, количество позиций.
- Действия: открыть PDF, отправить (если `saved`), удалить, копировать, открыть детали.
- Фильтр по статусу; пагинация.
- После очистки cookie гостевые заказы недоступны в списке; PDF можно получить у админа/менеджера. Это ограничение MVP зафиксировано в ADR-008.
- Post-MVP: аккаунты, восстановление доступа, синхронизация между устройствами.

### 5.7. PDF

- Формат A4, книжная ориентация, поля 15 мм.
- Страница 1: логотип, реквизиты, заголовок «Счёт-заказ № … от …», покупатель, таблица позиций (фото, наименование/SKU, опции, габариты, кол-во, цена, сумма), итоги, НДС, комментарий.
- Страница 2: 2D-план с площадью и подписью.
- Страница 3: 3D-вид пользователя и общий вид.
- Страница 4: фронт и профиль (ортографические виды).
- Колонтитул: страница N из M, номер заказа, контакты, ссылка/QR на заказ.
- Кириллица, встроенные шрифты (Roboto/Inter), сумма прописью (если включено).
- PDF сохраняется в volume и привязан к заказу; повторная генерация админом возможна.
- Настройки: логотип, реквизиты, VAT (нет/включён/сверху), ставка, префикс и формат номера, текст примечания.

### 5.9. Справочник свойств

- Свойство: код, наименование, нормализованное наименование, тип, единица, множественность, обязательность по умолчанию, фильтруемость, показ в карточке/PDF, подсказка, сортировка, активность.
- Типы MVP: `string`, `text`, `number`, `boolean`, `enum`, `color`.
- Параметры: код, подпись, нормализованная подпись, HEX/RAL для цвета, сортировка, активность, доплата (глобальная).
- Уникальность:
  - наименование свойства уникально без учёта регистра, с обрезкой и схлопыванием пробелов, нормализацией `ё → е`;
  - код уникален;
  - подпись параметра уникальна внутри свойства;
  - сервер возвращает понятную ошибку `PROPERTY_NAME_EXISTS`;
  - при похожих названиях (Левенштейн ≤ 2) — предупреждение, но не блокировка.
- Нельзя удалить свойство/параметр, используемый товаром, без явного подтверждения и отвязки.
- Изменение справочника не влияет на уже сохранённые заказы (там снимок).

### 7.4. Аутентификация и сессии

- Пароли: `crypto.scrypt` (N=16384, r=8, p=1), соль 16 байт, формат `scrypt$N$r$p$salt$hash`; сравнение — `timingSafeEqual`.
- Сессия: запечатанная cookie (`iron-session`), HttpOnly, Secure (prod), SameSite=Lax, TTL 7 дней (админ) / 30 дней (гость).
- Гостевая сессия: случайный ID (32 байта) в cookie; в БД заказа хранится HMAC от ID, не сам ID.
- CSRF: токен в сессии, отдаётся в `GET /api/auth/me`; для POST/PATCH/DELETE требуется заголовок `X-CSRF-Token`.
- Вход: rate limit 5 попыток / 15 минут / IP+email; блокировка на 15 минут; лог попыток в Pino.
- Роли: `admin`, `manager`, `customer` (post-MVP). Проверка на каждом admin-роуте.
- Админ создаётся CLI: `npm run create-admin -- --email ... --password ...` (или `ADMIN_*` в env при первом старте). Пароль в репозитории не хранится.
- Выход: очистка cookie, редирект на `/admin/login`.

### 7.5. Файлы

- Публичные: фото каталога, модели, логотип — `uploads/public/...`, отдаются с `Cache-Control: public, max-age=31536000, immutable` (имена хэшированные).
- Приватные: изображения заказов, PDF — `uploads/private/orders/<orderId>/...`, только через API.
- Загрузка: `multer`, лимит, проверка MIME по сигнатуре (`file-type`), расширение, размер; изображения — `sharp` (resize, rotate, JPEG/PNG), SVG запрещён.
- Имя файла: `ulid` + безопасное расширение; исходное имя — только в БД.
- SHA-256 для контроля дублей и целостности.
- Очистка orphan-файлов — задача по расписанию (post-MVP).

### 7.6. PDF

- `pdfmake` + Roboto (regular/bold/italic) в `apps/server/src/templates/fonts`.
- Документ собирается из `order` + `order_items` + `order_images`; изображения читаются с диска.
- Генерация в `worker_threads`, чтобы не блокировать event loop; таймаут 60 с.
- Результат: `uploads/private/orders/<id>/order-<number>.pdf`; запись в `files` + `orders.pdf_file_id`.
- Идемпотентность: повторный вызов возвращает существующий PDF, если `force` не передан.
- Ошибки: `PDF_IMAGES_MISSING`, `PDF_GENERATION_FAILED`; клиент показывает понятное сообщение.

### 7.7. 3D-модели

- Поддержка MVP: `.glb`, `.gltf` (только self-contained), `.stl` (binary/ASCII).
- Материал по умолчанию: сталь (`metalness 0.85`, `roughness 0.35`), цвет из опции; материалы GLB сохраняются;
  `extras.tintable = false` защищает неокрашиваемые поверхности от RAL-цвета.
- Оптимизация (этап 9): worker читает STL/GLB, сваривает вершины, упрощает через `meshoptimizer` (WASM), экспортирует GLB; оригинал сохраняется.
- Калибровка: `model_transform` JSON — поворот по осям, масштаб (равномерный/покомпонентный), смещение, режим подгонки.
- Автоподгонка: центр по XZ, низ на Y=0, равномерный масштаб по `min(W/bboxX, D/bboxZ, H/bboxY)`; предупреждение при расхождении пропорций > 5%.
- Исходная модель `models/Тележка PRF-E.stl`: binary STL, 176 672 треугольника, bbox 503.7 × 858.5 × 855.1 мм, не watertight, 253 компонента. Оси требуют калибровки в админке. Используется как seed-товар.

## 8. Модель данных (MySQL)

Общие правила:

- ID: `BIGINT UNSIGNED AUTO_INCREMENT`; публичные идентификаторы — `CHAR(26)` ULID.

- JSON-поля: `room_json`, `totals_json`, `product_snapshot`, `placement`, `model_transform`, `camera_json`, `meta`.

- Внешние ключи обязательны; удаление товара не ломает историю заказов (снимок + `ON DELETE SET NULL`).
- Миграции только через `drizzle-kit`; ручные правки схемы запрещены.

## 10. Геометрия, координаты и алгоритмы

### 10.1. Система координат

- Мир: X вправо, Y вверх, Z на зрителя (к передней стене). Единица — сантиметр.
- Пол: Y=0. Полигон комнаты задаётся в плоскости XZ.
- 2D-план: экранный X = мир X, экранный Y = мир Z. Камера сверху.
- 3D: камера по умолчанию в (+X, +Y, +Z), смотрит в центр.
- Фронт: камера на +Z, смотрит в −Z. Профиль: камера на +X, смотрит в −X.
- Угол поворота мебели: градусы, по часовой стрелке при взгляде сверху; 0° — «лицом» к −Z (в глубину комнаты), спинка к +Z.
- Мебель: позиция — центр footprint (X,Z), низ на Y=0 (или `elevationCm` для настенного монтажа).

### 10.2. Полигон комнаты

- Прямоугольник: `[[0,0],[W,0],[W,D],[0,D]]`.
- L-форма: `[[0,0],[W,0],[W,d1],[w1,d1],[w1,D],[0,D]]`.
- Площадь — формула шнурков, по модулю; периметр — сумма длин.
- Принадлежность точки — ray casting; для L-формы корректно работает.
- Выход за полигон: любая вершина OBB снаружи или пересечение рёбер OBB с рёбрами полигона.
- Стены: сегменты полигона; для коллизий используется внутренняя граница; толщина стен — только визуал.
- Отражение L-формы: `w1 → W - w1`, `d1 → D - d1` (с пересчётом полигона).

### 10.3. Footprint и коллизии

- Footprint товара — OBB `W × D` (габариты из карточки, не из меша), повёрнутый на `rotationDeg`.
- SAT для OBB vs OBB; допуск 0.5 см (настраивается).
- OBB vs полигон: все 4 угла внутри + нет пересечений рёбер; для L-формы обязательно оба условия.
- Коллизии:
  - `ITEM_OVERLAP` — пересечение с другой мебелью;
  - `OUTSIDE_ROOM` — выход за полигон;
  - `TOO_CLOSE_WALL` — меньше минимального зазора (post-MVP);
  - `DOOR_BLOCKED` — post-MVP.
- Критические ошибки блокируют отправку заказа; предупреждения — нет. Настройка в админке.
- При добавлении товара: попытка поставить в центр; если занято — спиральный поиск свободной позиции с шагом 10 см; если не найдено — поставить в центр с предупреждением.

### 10.4. Привязки

- Сетка: 1/5/10 см (по умолчанию 5).
- Стена: если расстояние от края OBB до сегмента < 8 см (в экранных px с учётом зума), прижать вплотную; угол = нормаль стены; галочка «зазор 0/2 см».
- Другие предметы: выравнивание краёв/центров с порогом 5 см; показывать направляющие.
- Поворот: шаг 15° по умолчанию; Shift — свободный; кнопки ±90°, ±15°; ввод числа.
- Перетаскивание: порог 3 px, чтобы не срабатывал клик; курсор `grabbing`.
- Undo/redo: команды `add`, `remove`, `move`, `rotate`, `options`, `room`, `qty`; объединять непрерывный drag в одну команду.

### 10.5. Вписывание камеры 3D

- AABB сцены: комната + мебель (с учётом высоты).
- Перспектива: `distance = radius / sin(fov/2)`, поправка на aspect; позиция по сферическим углам (азимут 45°, elevation 25–30°), target — центр AABB, margin 1.15.
- Ортография: `frustumHeight = max(bboxHeight, bboxWidth/aspect) * margin`, `frustumWidth = frustumHeight * aspect`.
- Фронт/профиль: ортографическая камера, target — центр AABB, позиция по оси, up = +Y.
- Перед захватом: дождаться загрузки всех моделей, шрифтов и двух кадров `requestAnimationFrame`; временно отключить UI-слой, gizmo, сетку.

### 10.6. Масштабирование модели

- Исходный bbox в мм; целевые габариты в см.
- `fitMode: "uniform"` — один масштаб на все оси (рекомендуется).
- `fitMode: "nonuniform"` — точная подгонка по W/D/H (только если пропорции модели заведомо неверны).
- Порядок: поворот → масштаб → смещение; низ на Y=0, центр по XZ.
- Если расхождение габаритов > 5% — предупреждение в админке и бейдж «модель требует калибровки».

## 12. PDF

- `pdfmake`, A4, поля 15 мм, шрифт Roboto (кириллица).
- Структура документа:
  1. Шапка: логотип, реквизиты, контакты.

- Если изображения отсутствуют — плейсхолдер с подписью (настройка `allowPdfWithoutImages`).
- Имя файла: `order-<number>.pdf`; число страниц проверяется тестом.

## 13. Безопасность

- **Заголовки:** Helmet; CSP `default-src 'self'`; `img-src 'self' data: blob:`; `script-src 'self'`; `style-src 'self' 'unsafe-inline'` (Konva/инлайн-стили); `worker-src 'self' blob:`; `connect-src 'self'`; `frame-ancestors` — настраиваемый список (для iframe).
- **Cookie:** HttpOnly, Secure, SameSite=Lax; при iframe — SameSite=None + Secure + предупреждение о third-party cookies.
- **CSRF:** double-submit/сессионный токен; проверка для всех мутаций.
- **Auth:** scrypt, timing-safe, лимиты, блокировка, ротация сессии после входа.
- **Доступ:** проверка владельца заказа, роли, токена; IDOR-тесты.
- **Файлы:** белый список расширений/MIME, проверка сигнатуры, лимиты, случайные имена, запрет SVG/HTML, отдача с `Content-Disposition` для приватных.
- **Валидация:** Zod на всех входах; защита от SQL-инъекций через Drizzle; XSS — React escaping, описания как текст.
- **Секреты:** только env, `.env` в `.gitignore`, `.env.example` без значений.
- **Логи:** без паролей, токенов, полных ПД; request id.
- **Rate limit:** login, создание заказа, загрузка, PDF.
- **Приватность:** согласие, ссылка на политику, удаление, ретенция, доступ только владельцу/админу.
- **Зависимости:** `npm audit` в CI, фиксация версий, лицензии.

## 19. Правила работы агента

1. **Сначала прочитать AGENTS.md** и следовать этапам.
2. **Не менять архитектуру** (БД, стек, PDF, auth) без обновления ADR и согласования.
3. **Не добавлять TypeScript, PHP, JSON-файловую БД, CDN.**
4. **Маленькие коммиты** с сообщениями `feat(scope):`, `fix(scope):`, `test(scope):`, `docs(scope):`.
5. **Сервер — источник истины** для цен, прав, валидации и статусов.
6. **Снимки заказов неизменяемы**; любые изменения каталога не должны менять старые заказы.
7. **Секреты только в env**; `.env.example` обновлять.
8. **Миграции только вперёд**; destructive — с бэкапом и подтверждением.
9. **Не реализовывать post-MVP** без явного запроса.
10. **При неоднозначности** — выбрать дефолт из раздела 20 и зафиксировать в журнале решений.
11. **Проверять сборку в Docker**, а не только локально.
12. **Обновлять чеклист этапа** после выполнения.
13. **Не оставлять `console.log`** в продакшен-коде; использовать Pino.
14. **Русский UI**, тексты без англицизмов, где есть понятный аналог.
15. **Доступность и производительность** — часть приёмки, а не «потом».

## 22. Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Тяжёлые STL (176k+ треугольников) | Низкий FPS, память | Оптимизация, LOD, лимит, ленивая загрузка |
| Некорректные единицы/оси моделей | Мебель неверного размера | Калибровка, bbox, предупреждения, seed-проверка |
| PDF блокирует event loop | Таймауты | worker_threads, лимиты, очередь |
| Гостевые заказы теряются | Недовольство | Токен-ссылка, письмо, post-MVP аккаунты |
| iframe + third-party cookies | Не работает вход | Reverse proxy/поддомен, предупреждение |
| Рост uploads | Диск | Лимиты, сжатие, очистка, бэкап, квоты |
| Конкурентная нумерация | Дубли номеров | Транзакция + `FOR UPDATE`, уникальный индекс |
| Ошибки миграций | Простой | Бэкап, тест на копии, идемпотентность |
| Утечка ПД | Юридические риски | Доступ, логи, согласие, ретенция |
| Сложность UX планировщика | Отток | Прототип, тесты с пользователями, подсказки |
| WebGL недоступен | Нет 3D | Fallback, 2D + сообщение |
| SMTP-доставка | Письма в спаме | SPF/DKIM, тест, повтор |
| Scope creep | Сроки | MVP-границы, backlog, этапы |
